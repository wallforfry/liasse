# @liasse/web

## 0.2.0

### Minor Changes

- 57b9e49: A document in `needs_review` says what to review. `GET /documents/:id?include=review` and `get_document` return a `review` part: the current threshold, the reasons the document is flagged (`low_confidence`, `type_pending_extraction`, `type_fallback`, `type_untyped`, `reextraction_failed`, `flagged_at_settlement`, `rejected_values`), and how sure the pipeline is of its type and of each core value and field, with the page and quote it was read from.
  
  A correction (`PATCH /documents/:id`, `update_document`) takes `confirm`, the core values or fields that are right as they are, each with the value it was read with: a confirmation never rewrites the value, makes it manual and clears `needs_review` like a correction. A value that changed since it was read refuses the correction with `value_changed`.
  
  The web UI shows a flagged document with a "To review" card: the reasons in sentences, the type to accept or change, and each doubtful value to accept, reject or edit, sent as one correction; a change of type leaves the fields to the extraction for the new type.
- 7db033b: The state of consolidation runs can be followed: `GET /consolidation/runs` (`listConsolidationRuns` in the SDK) lists the latest runs with their status, attempts and the error of a failed attempt. The Changes screen of the web UI shows where the latest run stands, follows it until it ends, says when it finished or failed, and reads the changes again. `CONSOLIDATION_TRIGGERS` and `ConsolidationTrigger` now come from `@liasse/contract/domain`, no longer from `@liasse/core/consolidation`.
- 12f6a23: The `entity` filter of search keeps the documents that name the entity in any entity field, in `core` or in the fields of their type, each item of a list field included, where it read `issuer` and `recipient` only. `GET /documents` (`listDocuments` of the SDK) takes the same `entity` filter, by the id of the entity. The document list of the web UI has an entity filter, picked by a name or an alias, which applies to the list and to its search.
- 6ac0866: The Graph page moves like Obsidian's: the graph settles into shape on screen under a live force simulation, a node can be pulled and its neighbours follow, hovering a node lights it and its neighbours, and documents show their labels once zoomed in. With reduced motion asked for, the graph is settled before it shows and only a pulled node moves.
- 16fa6f7: A graph of the archive. `GET /graph` (`graph` of the SDK) answers the most recent documents with their types and parents, the subjects they are about and the entities they name, and the links found between documents, private documents only when asked. The web UI draws it on a Graph page: pan and zoom, hide a kind of node, and select a node to see what it is joined to and open its document or type.
- 69d6c97: A consolidation run can be asked for by hand: `POST /consolidation/runs` (`requestConsolidationRun` in the SDK) queues one at once, unless a run due at once already waits, and the Changes screen of the web UI has a "Run consolidation" button.
- 3e9b8c4: Classification no longer files a document under an unrelated type. The model reuses a candidate only when it truly describes the document, and proposes a new type otherwise. A new type that cannot be created (daily quota reached, private document with an external embedder, proposal refused twice) leaves the document without a type, in `needs_review`, instead of giving it the closest candidate with a confidence of 0: the type provenance and the `review` part say why in `refusal` (`quota_exceeded`, `private_document`, `invalid_proposal`, `rejected_type`), and the `classification` event in `type_refusal`. The outcome `fallback` is no longer assigned; documents classified before keep it.
  
  `reclassify_document` (`POST /documents/:id/reclassify`) whose new type cannot be created changes nothing: the document keeps its type, values and status, and a failed `classification` event carries the reason as its `error_code`. With `new_type`, a slug that names another existing type is refused instead of taken.
  
  The description of the MCP tool `create_type` says it is the way to file such a document: it is outside the daily quota of classification, and `update_document` then sets the type. The web UI says why a document has no type.
- 6910894: The type of a settled document can be decided again when the one it got is wrong: `POST /documents/:id/reclassify` answers 202 with the document, the MCP tool `reclassify_document` does the same, and the SDK has `reclassifyDocument`. The request may carry a `hint` (cut to the length of an upload hint) and `new_type`, which asks for a new type only. A `reclassify_document` job asks the model again without the rejected type, tells it that a person said that type is wrong and what they added, then changes the type as a manual correction does, with the provenance of the model, and queues the re-extraction that settles the document. A document that is not `indexed` or `needs_review`, or has a processing, re-extraction or reclassification pending, is refused (`document_not_settled`); an unknown or deleted one is not found. The hint waits on the document (`documents.reclassification_hint`, blanked by a deletion), never in the job. `@liasse/contract` now holds the definitions of the core fields (`CORE_FIELDS`, `CORE_FIELD_NAMES`, `KEY_DATES_FIELD` in `/registry`, no longer exported by `@liasse/core/registry`) and `SETTLED_STATUSES` (in `/domain`), and the edit tab of the web UI edits every core field with the editor of its definition, filled or not, and chooses the type of a document by hand, as a correction.
- 6ba9355: `GET /documents/:id` and `get_document` answer `analysis_pending`: whether a processing, re-extraction or reclassification of the document is queued or running, while its status stays `indexed` or `needs_review`.
  
  The web UI asks for the type to be analysed again from the review of a `needs_review` document, as a third choice for its type next to Accept and Change, with an optional hint; the model creates a new type when none fits, without a checkbox. The document page follows a pending analysis from `analysis_pending`, so a reload or leaving the page no longer loses it, and says how it ended: with the new type, failed with its code, or left alone because the document changed first.
- 8bb948c: The models of a provider can be listed from the settings. `POST /settings/models` (`listSettingsModels` of the SDK) takes the endpoint of the language models or of a remote embedder as the form holds it, with the stored key when the key is kept, and answers the ids the provider lists, or why it listed none.
  
  On the settings page, each model field has a button that opens this list, searchable, next to the input, which still takes any id typed by hand.
- 0212ac4: A type can be drafted by the text model. `POST /types/suggestion` (`suggestType` of the SDK) takes a sentence on the documents the type is for and answers with a slug, a description, a parent and fields, without creating anything.
  
  The "Create a type" dialog of the web UI has two tabs: "Describe it", where the text model drafts the type from a sentence, and "Define it", the form, which the draft fills for review before the type is created.
- 1194426: The upload page takes several files at once. They are sent one after the other with the same hint and privacy, and a list shows the state of each: waiting, uploading, uploaded or already in Liasse (with a link to the document), or the reason the server refused it. A refused file does not stop the others; a lost session stops the batch and opens the login page. A single file still opens its document once uploaded.
- e40a8a6: The web UI creates the first account. While the server has none, every route, the login page included, shows the onboarding instead: the setup token the server printed to its logs, the account (name, email, password typed twice, with the length rules of the server), the language models and the embedder, each with a check through `POST /api/setup/check`, then a summary. Finishing calls `POST /api/setup`, signs in and opens the documents. A wrong token returns to its step, a setup finished elsewhere leads to the login page, and a field the server refuses opens its step with the message. The token, the keys and the password stay in the memory of the page.
- 65a9749: The search moves into the document list: a search box above the filters ranks the documents by relevance and shows the passages that match, with the type and status filters of the list applied to it. The review queue gets the same box. The separate Search page and its menu entry are gone, and the command palette opens its search on the document list.

### Patch Changes

- 9f4321d: A review refused because a confirmed value changed since the document was read now reads the document again and says so, instead of leaving the old values on screen until the page is reloaded.
- 6e6ae3d: While a search changes, the results of the previous one stay on screen dimmed, marked busy for assistive technology, until the new ones arrive.

## 0.1.0

### Minor Changes

- edaa336: Authentication moves to better-auth: accounts with a password, database sessions that survive a restart, API keys, and OAuth 2.1 for MCP clients. The first account is created at startup from `AUTH_BOOTSTRAP_EMAIL` and `AUTH_BOOTSTRAP_PASSWORD` while no account exists; `AUTH_SECRET` (32 characters or more) and `AUTH_SESSION_TTL` (`7d`) configure the sessions.
  
  The REST API takes an API key as `Authorization: Bearer <key>` or the session cookie, and a change made with the cookie needs the `Origin` of `PUBLIC_URL`. `/mcp` takes an API key or an OAuth access token issued for `PUBLIC_URL/mcp` (when `PUBLIC_URL` is https or on the loopback), never the cookie, and answers a refused request with the RFC 9728 challenge. The auth server answers under `/api/auth` and its discovery documents under `/.well-known`; sign-in is limited to 5 attempts a minute per socket address.
  
  The web UI is always mounted under `/ui`. It signs in with an email and a password, changes the password, creates, lists and revokes API keys, and holds the login and consent pages of the OAuth flow.
  
  `@liasse/contract` exports `AUTH_BASE_PATH`, `MIN_PASSWORD_LENGTH` and `MAX_PASSWORD_LENGTH`. `@liasse/core` has a new `auth` subpath and a migration for the tables of better-auth.
- 14d3f24: The web UI lists the MCP clients connected through OAuth (client id, name, redirect URIs, consented scopes, live tokens, dates) and revokes one after a confirmation. A revoked client loses its refresh tokens, consents and authorization codes not yet redeemed, and `/mcp` refuses every access token issued to it before the revocation, even when the client registers again.
  
  The auth server answers `GET /api/auth/mcp-connections/list` and `POST /api/auth/mcp-connections/revoke` for a signed-in person; `@liasse/contract` exports their schemas and paths. `/mcp` now also refuses an access token whose client was removed, disabled or revoked. `@liasse/core` has a migration for the table `oauth_client_revocations`.
- 02ab8b1: Each document keeps a processing log: every stage that succeeded and every attempt of its jobs that failed, with the stage, the status, the attempt, the error code and class, whether it is retried, the model, and counts such as the values the model returned that were rejected. Nothing read from the document is logged. The 100 most recent events are kept per document and removed with it.
  
  `GET /documents/:id/events` answers the log, the SDK reads it with `listDocumentEvents`, the MCP tool `get_status` adds it as `events`, and the document page of the web UI shows it in a Processing tab. A re-extraction or a re-indexing that fails in a way another attempt cannot fix now ends its job at once, as `process_document` did.
- 55ec70b: A model provider that refuses a call now says why. An event of the processing log of a document has `http_status` and `provider_code` (the error type and code of the provider, a network code, or `timeout`) and the `model` of a `model_provider_failed` failure, and the Processing tab of the web UI shows them under the error code. The `job_failed` line of the server log names the class of the cause and, for a provider failure, its provider, model, HTTP status and code. A migration adds the two columns to `document_events`.
- c0a2f44: `POST /types` creates a type by hand, `provisional` like one the pipeline creates, judged by the naming rules, primitives and two-level hierarchy of the registry under its lock; a refusal answers 400 with the code of the registry. The daily quota of new types does not refuse it. The SDK gains `createType`, and the web UI a Types page that lists the types with their status, fields and document counts, shows each type, and creates one.
- ccd3c27: The web UI is a single-page application, `@liasse/web`, made with Vite, React and shadcn components: document list with status, type and privacy filters, the review queue, the document page with its correction and deletion, search, upload and the consolidation changes, in a sidebar layout with a command palette (Cmd or Ctrl+K), toasts and a light or dark theme. It calls the REST API through the SDK with the session cookie and renders document content as text only.
  
  The server serves its build under `/ui` and refuses to start without it; `GET /` redirects there. The policy of `/ui` admits the scripts and stylesheets of the build and a per-request style nonce, never `unsafe-inline` or `unsafe-eval`. `@liasse/contract` exports `CSP_NONCE_META_PROPERTY`, and `createLiasseClient` takes `session: true` for a page served by the server.

### Patch Changes

- f4ff6f1: The Type field of the document correction form is a searchable list of the registry's types, matched by slug, alias or description, instead of free text that the server refused when no type had that slug.
